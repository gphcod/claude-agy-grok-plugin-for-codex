- **Stop path (A7.5).** `runManagedTurn` snapshots the owned descendants, SIGTERMs the child's process group, then SIGKILLs every identified row after `GRACE_MS` (3 s, bounded by the retry interval; `taskkill /T /F` on Windows). ## 2026-10-31 S2.6: entry wiring

- **Order (A4, S2.6).** `main()` parses argv and `--cwd`, reads the text (no stdin for control verbs, bare `review` and `--next-input`), applies the guards (five depth variables → exit 1; a state root inside realpath(cwd) → exit 1), looks the request id up and replays before any selector, catalog, adapter or preflight, then resolves the provider (`--to`, or the job or thread record; a conflicting `--to` → 2; an ambiguous bare id → 2), imports `./lib/providers/<p>.mjs` (absent → 2 `provider <p> not available in this build`), resolves tier, model and effort, runs the cached preflight, claims the request id, and runs the managed turn. Text is read in step (1) because the fingerprint (step 3) covers it.
- **The workspace is realpath(cwd)** for the state-root guard and for `--last`/bare `wait`/bare `cancel` (A7.1, A7.2); the Git root is resolved only by reviews.
- **Native thread ids must be known to council** (a job or a thread record) before `reply` or `task --thread` resumes them; GROKX accepted any UUID. A7.3 forbids adopting a native thread across workspaces, and an unrecorded id carries no workspace to check. A known thread always continues in its recorded cwd; a missing one exits 2.
- **Preflight order.** Sandbox descriptors (`dir`, `file`, `listener`, `process-table`) run before the cached probes (`exec`, `network`), so a blocked resource exits 1 with zero probes as well as zero submissions.
- **Request claim after preflight.** A fresh request id is claimed after preflight, immediately before admission; a blocked preflight or a usage error leaves no reservation. A turn refused before preparing (a busy thread) releases its reservation, so the id may run again (A7.4: "a claim that fails before preparation completes is released"); a turn that prepared keeps its tombstone and replays its outcome, failure or cancellation included. An abandoned reservation (companion gone, nothing prepared) is released by the replaying call, which exits 2 telling the caller the same id can run again.
- **The fingerprint includes `--deadline` and `--inactivity-timeout`** (as CLAUDEX: "a changed deadline still conflicts") and excludes `--json`, `--request-id` and `--timeout`. *Superseded at S2.8 (F19): both timers are excluded, as on the twin.*
- **Adapter calls the entry makes**: `buildTurn(request)` receives `{verb, text, prompt, instructions, contractPath, model, effort, resume, threadId, cwd, env, schemaPath, structured, readOnly, web, allowCommands, maxTurns, maxBudgetUsd, policy, agent, jobDir}`; the entry adds the five guard variables to whatever environment the adapter returns. `finalizeReview` returns the schema-shaped object (or `{structured}`); the core validates, reconciles the ledger and publishes coverage (`finalizeReviewTurn`). `reviewPlan(review, {adversarial})` picks the schema carrier (`embed` makes the batch prompt carry the schema text). `probe(launcher)` is run fresh by `setup` and by `models --refresh`.
- **Defaults.** Tier `consult` for ask/review/reply on a new thread, `exec` for task (GROKX `rescue`); a reply or `task --thread` inherits model, effort and tier unless `--tier`, `--model` or `--effort` is given, and an explicit value persists. Timeouts from GROKX: inactivity 1200 s, deadline 14400 s, `wait` 90 s, `cancel` 30 s; rounds 9 unless `--rounds` or `COUNCIL_CODEX_ROUNDS`.
- **Footer.** `batch i/n` is printed only when a review has more than one batch; `unreviewed N` counts unsupported input only (pending saved batches are `pending`, A5.2).
- **macOS ownership.** Where the process table gives only text (macOS `ps`), a row is owned only when it ends with the job's complete recorded child arguments and its program is the recorded launcher or the same native binary (GROKX's rule, generalized); the adapter's `ownsProcess` decides for argument vectors (Linux, Windows). ## 2026-10-31 S2.9: close remaining ownership and hook gaps (Codex and Argon confirmations of S2.8)

- **Group members (execution.mjs `ownedExecution`).** Every live process in group `job.pid` that no evidence adopted is `unverified` (ownership unknown, never signalled, claim kept), whatever its birth time: S2.8 dropped members born after `endedAt` and members seen beside a reused live leader, so the confirming cancel could release the claim while a surviving descendant's child ran. The one exception: a live process holds pid `job.pid` with a creation time other than the recorded leader's, so the group id was reused; members born at or after that new leader are unrelated, and any member that predates it (Argon's 12:00:01 member beside a 12:00:05 holder) stays unverified.
- **Leader identity.** The lifecycle records `job.leader` (pid + creation time from one scoped process query) right after spawn, and persists it with the launch, so a turn shorter than a heartbeat has evidence; heartbeats, stop and exit snapshots add descendants as before. `pidWindow` is gone: a missing `job.leader` means no leader identity, and on darwin no persisted identity adopts anything then. Not recorded on Windows (its query costs most of a second; no groups there).
- **Paths with spaces (`ownsRecordedInvocation`).** Matched by suffix: the row ends with the exact recorded child-argument string, and the program part is the recorded launcher, or equals the provider binary or ends with `/<binary>`. A program part with spaces counts as a path only when that file exists (`/Users/First Last/.grok/bin/grok`); otherwise it may be a wrapper's arguments, so the row is ambiguous (`null`) and, with the adapter's operand evidence, makes ownership unknown rather than gone.
- **Deferred afterTurn order (lifecycle.mjs `cancelManaged`).** The `after-turn` marker is written first, then `afterTurn` runs, then the job is marked stopped and its claims released. A failure before the hook begins (ENOSPC on the marker) leaves the job cleanup-pending with its claim and exits 1; a retry runs the hook once and releases.
- `execution.mjs` re-pinned; tests in tests/core-review-fixes.test.mjs and tests/core-execution.test.mjs, each checked to fail against the S2.8 modules.

## 2026-10-31 S2.10: distinguish a running hook from a settled one (Codex confirmation of S2.9)

- The deferred-afterTurn reservation `after-turn` now carries a state: `running` with the holder's pid and identity (created whole and exclusively, a private file linked into place), then `settled` with the outcome (an atomic rename). Only `settled` lets a cancel mark the job stopped and release its claims; S2.9 treated any existing reservation as done, so a concurrent cancel released the claim while the first cancel's hook still ran.
- A cancel that finds `running` under a live holder exits 20 (`running`) and touches nothing; under a holder that cannot be checked, or an unreadable record, exits 1 and touches nothing; under a holder proven gone it takes the reservation over (atomic rewrite, then a read-back that it holds it) and runs the hook again. `types.mjs` documents that afterTurn must tolerate a re-run. A settlement that cannot be stored keeps the claim (exit 1).
- Tests (tests/core-review-fixes.test.mjs, failing against S2.9): a barrier inside afterTurn with a second cancel during the hook; a takeover from a gone holder.

## 2026-10-31 S2.11: fresh holder check before takeover (Codex confirmation of S2.10)

- A cancel that reads a `running` after-turn reservation checks its holder with a fresh query taken after the read: the controller's new `scoped(pid)` (one `ps -p`/scoped query), or a fresh full snapshot for a controller without it. Not found in that query is gone (takeover); live or a failed query is running/unknown (exit 20 or 1, nothing touched). S2.10 used the table the cancel took before reading, which could predate the holder, so a second hook ran.
- `execution.mjs` re-pinned (`executionController().scoped`); test in tests/core-review-fixes.test.mjs reproduces Codex's scheduling and fails against S2.10.
